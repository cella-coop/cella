The files the co-op keeps: its own papers, members' receipts, workers'
employment records and members' records. A file is uploaded once and never
changes; what it is attached to is the graft's that attaches it.

## Entities

| Entity | Fields | Notes |
|---|---|---|
| file | `id`, `class`, `subject?`, `name`, `type`, `size`, `bytes?`, `hash?`, `uploader`, `uploaded` | `id` is `fi-0001` and up, its number four digits or more, so `fi-10000` follows `fi-9999`, in every list too, which orders ids by their number, never as text; `hash` the BLAKE3 of `bytes`, generated by the database; `class` the retention class of the personal data it holds, `none` for the co-op's own |

A file is named by the BLAKE3 of its bytes, which the database computes
(`cella.digest`), never the client, and which anyone holding the file can
compute again: the log commits to it, so a file shown later is the one
uploaded. It holds at most 10 MiB (`file.largest()`).

## Storage

The bytes are kept in Postgres, in the feat's own table, not on disk
beside it. A scope's database is the unit that moves, backs up and
replays ([trust](../../../../_corpus/doc/trust.md)): bytes on disk would
leave it, and a backup or a move would have to carry a second store in
step with the log. Erasure is the other reason: a personal file's bytes
are a column the notary redacts, like any other personal value. At the
pilot's size, a co-op's receipts and contracts, the database holds them
comfortably; a store of large media would want large objects or a blob
store behind the same table later.

The table is split by class into four parts, `file.shared` (`none`),
`file.receipt` (`expense-receipt`), `file.contract` (`payroll`) and
`file.record` (`profile`), so that each part registers its name
and bytes in `cella.personal` under its own class and erasure finds them
by it. Redacting the bytes empties the hash generated from them.

## Actions

| Action | Label | Why |
|---|---|---|
| `POST /api/file/upload` | confluent, `upload-file` | a file of the co-op's own is a fact, the uploader's; two commute; every person's right |

A personal file comes in through the graft that attaches it, in that
graft's write: a receipt with `expense-file`, an employment record with
`employment-file`, a member's record with `file-membership`. Each stores it with
this feat's spec, `storing`, and commits to it with `committed`.

## What the log keeps

Of the co-op's own file, its name, its BLAKE3 and its bytes, in base64
as the member signed them, which are no one's, so its entry folds to the
file. Of a personal file, a commitment to its name and to its BLAKE3,
the vault keeping them until erasure
([trust](../../../../_corpus/doc/trust.md#personal-data)), and never its
bytes. The request the member signs holds the bytes themselves, in
base64, so their signature covers the content; the receipt keeps only
its salted digest.

## Who opens a file

`file.opens(id, actor)`: the co-op's own files anyone may; a personal file
the person it concerns and who uploaded it. A graft that sees a power over
what a file records opens it to more: `file-membership` to whoever
holds a power over expenses, pay or members. The shell serves the bytes at
`/files/<id>/content` only where one of them opens it, as an attachment
unless it is a picture, a PDF or plain text, and sandboxed.

## Guards

- `file.fixed`, a trigger: a file never changes, but by the notary's
  redaction.
- `file.stored(id, class, subject)`: why a file is not the one a write
  stored, uploaded by the actor on the verdict date, of the class and
  about the subject named, and holding its bytes; every attaching graft's
  guard calls it.
- `file.uploads`, on `file:file:upload`: a file of the co-op's own,
  stored by this write.

## Schema

`file` (`core/sql/`): `file.file`, partitioned by class, numbered from
`file.number`; `file.largest()`, `file.opens`, `file.stored`. The app role
may select and insert; the guards role may select.

Every record names its owning circle, `circle`, a foreign key into
core's circles ([owning
circle](../../../../_corpus/doc/architecture.md#sql)): the root's, the
assembly's, unless the write that makes it names another.

## Folds

An upload folds by `core/sql/004-folds.sql` ([folds](../../../../_corpus/doc/architecture.md#folds)):
the co-op's own file under the id its entry names, uploaded by the
entry's actor on its day, with its name, type, size and the bytes its
entry keeps, which must hash to the BLAKE3 it names. The write it
publishes, `storing`, folds by `file.fold_storing`, which an attaching
graft's fold calls as its handler calls `storing`: a personal file in
its class's part, its name and bytes as the commitments its entry keeps,
the bytes' to their BLAKE3, written as erasure leaves them, its name
`redacted` and its bytes null, since a folded scope opens no commitment.

## Reads

Who reads a file at all, its name, class and bytes, is `file.opens`'s guard made a row-level policy (`sql/003-reads.sql`, [the pattern](../../../../_corpus/doc/architecture.md#sql)), in place of core's: the co-op's own files, whoever reads their circle ([reading](../../core/circle/index.md#reading)); a personal file, the person it concerns, who uploaded it and whoever holds a power a graft registers for its class (`file-membership`). A file its reader may not read is none to them: its page and its content answer 404, and no name or size is shown. The parts are read only through `file.file`, so its policy holds. A write's transaction reads every file.

## Shell

The `files` collection, out of the sidebar since a file belongs to the
record it is attached to and reached from the command menu, every file with its kind, size and
day; a file of the co-op's own uploaded from the New form; and a file's
page, its kind, type, size, uploader, whom it concerns and its BLAKE3, and
a link that opens it.

## Analytics

Its [analytical contract](../../../../_corpus/doc/architecture.md#analytical-contracts), `core/sql/analytics.sql`, publishes `file.classes` to the analytics shell: how many files each class keeps and their size. A file is personal data whole, so only these sums are shared. It is shared by `class`. Its view is declared a published query, in `core/ts/src/api/contract.ts`, which the web shell serves through the port as the analytics shell reads it.
