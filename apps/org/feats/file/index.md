The files the co-op keeps: its own papers, members' receipts, workers'
employment records and members' records. A file is uploaded once and never
changes; what it is attached to is the graft's that attaches it.

## Entities

| Entity | Fields | Notes |
|---|---|---|
| file | `id`, `class`, `subject?`, `name`, `type`, `size`, `bytes?`, `hash?`, `uploader`, `uploaded` | `id` is `fi-0001` and up; `hash` the BLAKE3 of `bytes`, generated by the database; `class` the retention class of the personal data it holds, `none` for the co-op's own |

A file is named by the BLAKE3 of its bytes, which the database computes
(`cella.digest`), never the client, and which anyone holding the file can
compute again: the log commits to it, so a file shown later is the one
uploaded. It holds at most 10 MiB (`file.largest()`).

## Storage

The bytes are kept in Postgres, in the feat's own table, not on disk
beside it. A scope's database is the unit that moves, backs up and
replays ([trust](../../../../_corpus/doc/trust.md)): bytes on disk would
leave it, and a backup or a move would have to carry a second store in
step with the log. Erasure is the other reason: a personal file's bytes
are a column the notary redacts, like any other personal value. At the
pilot's size, a co-op's receipts and contracts, the database holds them
comfortably; a store of large media would want large objects or a blob
store behind the same table later.

The table is split by class into four parts, `file.shared` (`none`),
`file.receipt` (`expense-receipt`), `file.contract` (`payroll`) and
`file.record` (`member-profile`), so that each part registers its name
and bytes in `cella.personal` under its own class and erasure finds them
by it. Redacting the bytes empties the hash generated from them.

## Writes

| Write | Label | Why |
|---|---|---|
| `POST /api/file/upload` | confluent, `self` | a file of the co-op's own is a fact, the uploader's; two commute |

A personal file comes in through the graft that attaches it, in that
graft's write: a receipt with `expense-file`, an employment record with
`file-worker`, a member's record with `file-member`. Each stores it with
this feat's spec, `storing`, and commits to it with `committed`.

## What the log keeps

Of the co-op's own file, its name and BLAKE3. Of a personal file, a
commitment to each, the vault keeping them until erasure
([trust](../../../../_corpus/doc/trust.md#personal-data)). The request the
member signs holds the bytes themselves, in base64, so their signature
covers the content; the receipt keeps only its salted digest.

## Who opens a file

`file.opens(id, actor)`: the co-op's own files anyone may; a personal file
the person it concerns and who uploaded it. A graft that sees a power over
what a file records opens it to more: `circle-file-member` to whoever
holds a power over expenses, pay or members. The shell serves the bytes at
`/files/<id>/content` only where one of them opens it, as an attachment
unless it is a picture, a PDF or plain text, and sandboxed.

## Rules

- `file.fixed`, a trigger: a file never changes, but by the notary's
  redaction.
- `file.stored(id, class, subject)`: why a file is not the one a write
  stored, uploaded by the actor on the verdict date, of the class and
  about the subject named, and holding its bytes; every attaching graft's
  rule calls it.
- `file.uploads`, on `file:file:upload`: a file of the co-op's own,
  stored by this write.

## Schema

`file` (`core/sql/`): `file.file`, partitioned by class, numbered from
`file.number`; `file.largest()`, `file.opens`, `file.stored`. The app role
may select and insert; the rules role may select.
