`cella` is the org app's Rust root (`apps/org/rs`, package `cella-cli`) and the repository's one entry point: every development and production task runs through it. It orchestrates the tools where their logic lives — cargo, cargo-pgrx, the Postgres binaries, pnpm and the node tools in `tools/` — as subprocesses from the workspace root, which it finds by walking up from the working directory, or else where the binary was built, so it runs the same from any directory. Each step prints one line, `ok` with its time and a summary, or `FAIL` followed by the tool's whole output; the exit code is the failing tool's. `-v` streams every tool's output instead. A missing tool fails with exit code 127 and says to run inside `nix develop`.

## Commands

| Command | For | What |
|---|---|---|
| `cella check [--no-sql]` | development | what a commit must pass: the feat check (`tools/feat-check.mjs`, its SQL boundaries skipped with `--no-sql`, and with them its reading of every action's power against the SQL that registers it and the mandates the fixtures adopt), the fixture check, the type check of the server layers and tools (`tsc`), the shell check (`svelte-kit sync`, then `svelte-check --fail-on-warnings` over the shell and every slice's client layers), the brand check, `cargo check` and clippy; no database |
| `cella check feats\|fixtures\|types\|shell\|brand\|rust` | development | one part alone; `brand` regenerates the brand's files in memory (`tools/brand.mjs --check`) and fails on each that differs from what `packages/brand` commits, or is missing or left over |
| `cella brand` | development | writes the brand's generated files from its `house.json` (`tools/brand.mjs`): its tokens, fonts, Starlight mapping, mark, wordmark, lockups and icons, at `packages/brand`'s root, removing any it no longer makes ([the brand](../../../packages/brand/index.md)) |
| `cella serve [--port PORT]` | development | the shell's dev server, Vite on `http://localhost:5173` by default, against the dev database: starts the cluster if it is stopped, and the analytics shell on the dev database, or reuses the one that runs on it, refused where the port's shell attaches another, applies any new migration, says if the database is unseeded, then runs until stopped. It sets `CELLA_DEV=1`, dev mode, whose sign-in page offers the fixture members: the browser derives the TEST-ONLY key of the one picked and signs with it, as with any device |
| `cella serve --prod [--port PORT] [--url URL]` | production | the shell built (`cella build`) and run as a scope's server on `127.0.0.1:PORT`, outside dev mode, against the dev database or the one `--url` names, migrated first: members sign in with their own devices and sign every action in the browser, and the sign-in offers no one. The server acts as `cella_app` whatever `--url` logs in as, so the row-level policies hold for every read; the URL's role is a superuser or a member of `cella_app`. It expects TLS in front, setting `x-forwarded-proto` (`PROTOCOL_HEADER`), and takes files up to 10 MiB (`BODY_SIZE_LIMIT=11M`) |
| `cella build` | production | builds the shell with adapter-node into `apps/org/ts/build`, a Node server (`node apps/org/ts/build`) that finds its database by the `PG*` variables or `DATABASE_URL` and listens on `PORT`, which `serve --prod` runs. It expects TLS in front: adapter-node takes the origin to be https unless `PROTOCOL_HEADER` names a proxy's header. A file up to 10 MiB needs `BODY_SIZE_LIMIT=11M`, above adapter-node's default of 512 KiB |
| `cella db start` | development | builds the extension, then starts the dev cluster or restarts it to load a rebuilt one; creates the cluster, its dev keys `.data/notary.key` and `.data/vault.key` and the database on first use, migrating it at once, since the analytics shell attaches as a role the migrations make; then starts the analytics shell on the dev database, or reuses the one that runs on it, refused where the port's shell attaches another |
| `cella db stop`, `cella db status` | development | stops the analytics shell, then the cluster; says whether the cluster runs, exiting 3 when stopped as `pg_ctl` does |
| `cella db reset [--db NAME] [--seed FIXTURE]` | development | drops, recreates and migrates a database on the cluster, the dev one by default, and with `--seed` loads a mock co-op into it, such as `lanterne`; a reset never leaves a database unmigrated |
| `cella db psql [ARGS…]` | development | psql on the dev database; arguments pass through |
| `cella analytics start [--db NAME \| --url URL] [--port PORT]` | both | the analytics shell ([architecture](../../../_corpus/doc/architecture.md#the-analytics-shell)): DuckDB 2.0 serving over quack on `localhost:PORT` (`CELLA_ANALYTICS_PORT`, 54343), the dev database or another on the cluster attached read-only as `cella_analytics`, or the one `--url` names, which must log in as that role. Its state is `.data/analytics/<PORT>/`: the token it answers to, made owner-only on first start, the SQL it starts with and a client attaches with, both owner-only, its pid and its log. It loads the flake's extensions from `CELLA_DUCKDB_EXTENSIONS`, then turns off every access outside and locks its settings, runs in the background reading a fifo it holds open, and is ready when it answers as `cella_analytics`; one answering as any other role is stopped. A shell serves one database: it keeps what it attaches in `.data/analytics/<PORT>/attach`, owner-only, and a start on a port whose shell runs reuses it only where it attaches the database asked for; any other start is refused, saying what the port's shell attaches, a URL without its password, and to stop it or take another `--port` |
| `cella analytics stop\|status [--port PORT]` | both | stops the shell; says whether it runs and what it attaches, a URL without its password, exiting 3 when stopped |
| `cella analytics query <SQL> [--json] [--port PORT]` | development | runs SQL in the shell as its client, read-only as `cella_analytics`, its views as `scope.<schema>.<view>`, printing a table or JSON rows |
| `cella analytics query --report <FILE> [--port PORT]` | development | runs a report definition in JSON through the port (`tools/report.mjs`), as a page would: checked against the views the slices publish, each reason printed and exit 2 when refused, else the result as JSON, stamped with the log's head ([the port](../core/analytics/index.md)) |
| `cella ext build` | development | packages the `cella` extension with `cargo pgrx package` into a fresh `.data/ext`, where the dev cluster loads it, with every script in the notary's `rs/sql/` staged beside the generated one: pgrx stages only the upgrade scripts, and an earlier version installs from its own |
| `cella migrate [--url URL]` | both | applies the migrations cascading down the feat tree (`tools/migrate.mjs`), on the dev database or on any database by URL, recording each by its stable id ([migrations](../../../_corpus/doc/architecture.md#migrations)); a database that recorded them by path moves to ids on its first run. Until launch a migration is rewritten in place, so a database that applied a file since edited, or one the tree no longer has, is refused before any runs, saying to rebuild it with `cella db reset`. Then, whenever a migration ran or one changed, it publishes the slices' analytical contracts, each `sql/analytics.sql`: the views published before dropped, each contract applied in tree order, each view granted to `cella_analytics` and read as it ([analytical contracts](../../../_corpus/doc/architecture.md#analytical-contracts)). The run is one transaction: one that fails leaves the database and its published views as it found them |
| `cella backup <DIR> [--url URL]` | production | backs the dev database, or the one `--url` names, up into a new owner-only directory: the dump (`pg_dump --format=custom`), the notary's and the vault's key files, the previous vault key's where `cella.vault_key_previous` is set and each kept in `cella.vault_keys_kept`, the scope's erasures (`erasures.json`, every tombstone of `vault.erased`, nothing personal), and a manifest of the database's name, the extension's version, the log's head, each vault key file's wrap id and the settings the database and its roles carry, which a dump leaves out. All of it is read at one point of the log: one repeatable-read transaction reads the manifest and the key paths and exports the snapshot `pg_dump --snapshot` dumps, and stays open while the key files are read. A key path that moved by the end refuses the backup, which then leaves no directory. Run on the database's host, as a user who reads the key files ([operations](../../../_corpus/doc/operations.md#backups)) |
| `cella restore <DIR> [--db NAME \| --url URL] [--erasures PATH]` | production | restores a backup into a new database on the dev cluster, the one backed up by default, or into an empty one at `--url`, such as a new host's: refuses unless the cluster installs the extension at the version backed up; writes each key file where the cluster reads it if it is missing, refuses if one there differs, and refuses a backup holding the previous vault key where the cluster sets no `cella.vault_key_previous`; writes each vault key kept from an earlier rotation into a path of `cella.vault_keys_kept` holding it or free, refusing where none is; makes the roles and the settings, loads the dump, refuses one whose vault names a wrap key none of its key files derives, saying that key's id, and before the database opens to the app re-applies through `cella.vault_reerase` the newest erasures it is given, a later backup's that `--erasures` names or its own, refusing a list older than its own; then checks that the log verifies, that its head is the backup's, and that every entry opens from the vault or folds as its erasure left it |
| `cella seed <fixture> [--url URL]` | development | founds a mock co-op from `apps/org/fixtures/`, such as `lanterne` (`tools/seed.mjs`), as one action, the log's first entry, the founding (`membership-motion:scope:found`): its form, its founders, its root circle and its founding motion, with the state it held before its log, signed by its first enrolled device in force, a founder's seated in its root |
| `cella import <kind> <file> --as <address> [--dry-run] [--url URL]` | development | brings a file from another tool into the scope as the member named (`tools/import.mjs`): each record read by the slice whose action it is and made through that action, signed with the member's TEST-ONLY fixture device as the dev server signs, and judged by the guards; `--dry-run` makes each action and rolls it back. Prints what each line came to and records the run in the import feat; an unknown kind lists the kinds: `members`, `contacts`, `fec`, `invoices`, `toggl`, `harvest`, `projects`, `tasks` |
| `cella test` | development | the guard primitives' tests, this CLI's tests, the notary's, the node tools' tests (`tools/_tests`), then the slice tests and the e2e scenarios; needs the dev cluster |
| `cella test notary` | development | the notary's `#[pg_test]`s ([the notary](../core/notary/index.md#tests)), on a cluster pgrx makes and drops. pgrx installs the extension where `pg_config` says, so it is handed one under `.data/notary-test` that names a share and a lib directory there, which the cluster loads from as the dev cluster does, with every script in the notary's `rs/sql/` staged there as `cella ext build` stages them, so the tests install each earlier version and upgrade it; a target directory of its own, `target/notary-test`, keeps that `pg_config` from rebuilding the workspace's bindings |
| `cella test slice [NAME]` | development | the slice tests, each feat's or graft's `_tests/*.test.ts`, or one slice's by its name, such as `transaction`: for each slice, `cella_test` is renewed and migrated with the app's core and that slice's part of the tree alone, unseeded and unbound (`cella.unbound`), so its tests write their rows below the notary; a slice that publishes an analytical contract is migrated so even with no test file, which applies its contract on its part alone and reads each view as `cella_analytics` |
| `cella test e2e [NAME]` | development | the scenarios across slices, `apps/org/ts/_e2e/*.test.ts`, or one by its file name, such as `admission`: the shell is built first (`cella build`), since `shell` drives its server; then for each, `cella_test` is renewed, migrated whole and seeded with Lanterne. The browser scenarios drive nixpkgs' Playwright browsers, which `cella` and the devshell export as `PLAYWRIGHT_BROWSERS_PATH`. Firefox launches with a home of its own under the temporary directory and without its content sandbox, as Playwright runs Chromium without its own, so it runs where the home is read-only, as a turn's on the box is. The rehearsal, `restore`, runs this binary (`CELLA_BIN`) against a throwaway cluster of its own, as a new host would; `upgrade` retires until launch ([upgrades](../../../_corpus/doc/operations.md#upgrades)) |
| `cella test guards\|cli\|notary\|tools` | development | one part alone; `tools` runs on the dev cluster, where migrate's tests make a database of their own, `cella_tools`, and drop it |
| `cella log verify [--url URL]` | both | runs `cella.verify_log()`, which checks every entry, the receipt it names and both signatures on it, the member's and the notary's, and prints the log's head and the scope's public key; a broken log fails, with the notary's warnings saying where |
| `cella vault sweep [--url URL]` | both | runs `cella.vault_sweep()` as the superuser on the verdict date: destroys the restricted keys whose legal clock has run out and completes each restricted erasure whose clock has, redacting its columns; prints a line for each subject and class it touched ([the vault](../core/notary/index.md#the-vault)) |
| `cella vault rewrap [--url URL]` | both | runs `cella.vault_rewrap()` as the superuser: seals every vault key under `cella.vault_key_file`'s wrap key, moving those that open only under `cella.vault_key_previous`; prints how many moved, after which the previous file may be destroyed ([operations](../../../_corpus/doc/operations.md#keys)) |
| `cella key init <PATH>` | production | writes a new scope signing key, the 32-byte Ed25519 seed `cella.key_file` reads, readable by its owner only and never over an existing file; prints its public key |
| `cella key init --vault <PATH>` | production | writes a new vault key, the 32 random bytes `cella.vault_key_file` reads, apart from the notary's, the same way |

The dev cluster is Postgres 18 in `.data/pg`, owned by the user, listening on 127.0.0.1 at `CELLA_PGPORT` (54342) with trust authentication and on no Unix socket, whose path a deep checkout's `.data` would make longer than the 107 bytes one may hold; the dev database is `CELLA_DB` (`cella`). Commands on it connect by the `PG*` variables. `--url` connects anywhere else instead and is handed to the node tools as `DATABASE_URL`; cella never reads `DATABASE_URL` from its own environment, so a production database is only ever named on the command line. Both `serve`s keep the shell's session key, 32 random bytes made owner-only on first use, in `.data/session.key` and hand it to the server as `CELLA_SESSION_KEY_FILE`, so sessions outlive a restart. They hand it the analytics shell too, its address as `CELLA_ANALYTICS` and its token's file as `CELLA_ANALYTICS_TOKEN_FILE`, which the port reads with `CELLA_DUCKDB_EXTENSIONS`.

## On the path

The flake's `cella` package is a wrapper that runs this crate with `cargo run -q -p cella-cli`, carrying the toolchain and pgrx's settings, DuckDB 2.0 among the toolchain and its extensions' directory as `CELLA_DUCKDB_EXTENSIONS`, so `cella` is on the devshell's path, rebuilds itself after a change and is instant otherwise; `nix run .#cella -- check` runs it from a checkout without entering the shell.

## Gates

The lanes gate a change by the forge's `gates` flow, `.corpus/flows/gates.toml`, run at the branch's tip (`corpus flow run gates --at <commit>`): its ops are `cella check` and then `cella test`, so the run logged over a commit is what a commit must pass and nothing else. Both run in the devshell (`nix develop -c`), so a run needs nothing on the path but `nix`, in a lane's checkout or the detached one `--at` makes. The check first fetches the lockfile's packages (`pnpm fetch`) into the pnpm store of the filesystem the checkout is on, which `cella`'s offline install reads; `cella test` first starts the dev cluster on ports of the run's own (`CELLA_PGPORT`, `CELLA_ANALYTICS_PORT`), so runs at once never meet on one, and stops it after, pass or fail; an e2e scenario that starts an analytics shell of its own takes its port from `CELLA_ANALYTICS_PORT` plus an offset of its own, never a fixed one, so it too meets no other run's. The e2e scenarios drive the browsers `BROWSERS` names, all three by default, on bacillus as on any host: the box's software GL driver, Mesa's EGL vendor under `/run/opengl-driver`, gives WebKit an EGL display, so a run there narrows no browser. Cella declares its flows rather than leaving corpus to infer them from `Cargo.toml` and `package.json`: the forge's `test` flow on a push runs the same two ops, and no flow runs a bare `cargo test`, `cargo fmt --check` or `npm test`, which gate nothing `cella` does not.

## Tests

`tests/help.rs` walks the command tree and runs the built binary's `--help` for every command, checks clap's own consistency, that an unknown command exits 2, and that `key init` writes an owner-only 32-byte key and refuses to overwrite it. `src/test.rs` checks that a test file is placed by where it sits: a slice test in a feat's or graft's `_tests/`, an e2e scenario in an app root's `_e2e/`, and nothing elsewhere.
