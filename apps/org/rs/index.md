`cella` is the org app's Rust root (`apps/org/rs`, package `cella-cli`) and the repository's one entry point: every development and production task runs through it. It orchestrates the tools where their logic lives — cargo, cargo-pgrx, the Postgres binaries, pnpm and the node tools in `tools/` — as subprocesses from the workspace root, which it finds by walking up from the working directory, or else where the binary was built, so it runs the same from any directory. Each step prints one line, `ok` with its time and a summary, or `FAIL` followed by the tool's whole output; the exit code is the failing tool's. `-v` streams every tool's output instead. A missing tool fails with exit code 127 and says to run inside `nix develop`.

| `cella test e2e [NAME] [--since REV] [--overlap]` | development | the scenarios across slices, `apps/org/ts/_e2e/*.test.ts`, or one by its file name, such as `fold`, Lanterne's year, which writes through every action the tree declares, fails naming any its log misses, and folds that log into a fresh database that matches every state table row for row: the shell is built first (`cella build`), since `shell` drives its server; then `cella_test_lanterne` is renewed, migrated whole and seeded with Lanterne once per run. The browser scenarios drive nixpkgs' Playwright browsers, which `cella` and the devshell export as `PLAYWRIGHT_BROWSERS_PATH`. Firefox launches with a home of its own under the temporary directory and without its content sandbox, as Playwright runs Chromium without its own, so it runs where the home is read-only, as a turn's on the box is. The dev cluster is Postgres 18 in `.data/pg`, owned by the user, listening on 127.0.0.1 at `CELLA_PGPORT`, else at the first port of the block a corpus worker is handed (`CORPUS_PORT`), else at 54342, so two lanes' clusters on one box never meet on one port, and hands it to every tool it runs as `CELLA_PGPORT`, the analytics shell's as `CELLA_ANALYTICS_PORT`, so a test meets the cluster cella started; it listens with trust authentication and on no Unix socket, whose path a deep checkout's `.data` would make longer than the 107 bytes one may hold; the dev database is `CELLA_DB` (`cella`). Commands on it connect by the `PG*` variables. `--url` connects anywhere else instead and is handed to the node tools as `DATABASE_URL`; cella never reads `DATABASE_URL` from its own environment, so a production database is only ever named on the command line. Both `serve`s and `preview serve` keep the shell's session key, 32 random bytes made owner-only on first use, in `.data/session.key` and hand it to the server as `CELLA_SESSION_KEY_FILE`, so sessions outlive a restart. ## Secrets

A development secret, an API key a task needs, lives in `secrets/dev.yaml`, a [sops](https://github.com/getsops/sops) file whose values are encrypted to the age recipients `.sops.yaml` names and whose keys stay readable; it is committed, and the repository being public, so is its ciphertext and the names of its keys. `sops` is on the devshell's path. `secret::get` decrypts one value by its key with the caller's age identity, sops's own (`~/.config/sops/age/keys.txt`, or `SOPS_AGE_KEY_FILE`), holds it zeroized, and hands it to the one tool that needs it in that tool's environment, never on a command line; no file or no such key is none, and a file that will not decrypt fails naming it. A secret already in the environment wins over the file's.

| Key | Read by |
|---|---|
| `unsplash_access_key` | `cella site photo add`, as `UNSPLASH_ACCESS_KEY` |

A person edits the file with `sops secrets/dev.yaml` from the repository's root, which decrypts it into their editor and encrypts it again on save. A recipient reads every version of the file, so one is added to `.sops.yaml` on purpose, the file re-encrypted with `sops updatekeys secrets/dev.yaml`, and a recipient lost means every value rotated.

## On the path

The flake's `cella` package is a wrapper that runs this crate with `cargo run -q -p cella-cli`, carrying the toolchain and pgrx's settings, DuckDB 2.0 among the toolchain and its extensions' directory as `CELLA_DUCKDB_EXTENSIONS`, so `cella` is on the devshell's path, rebuilds itself after a change and is instant otherwise; `nix run .#cella -- check` runs it from a checkout without entering the shell.

## Gates

The e2e run migrates the unseeded fold template and migrates and seeds Lanterne once, with no session left open on either template while its worker databases clone them. It prints each template's preparation time and each clone's time, separately from scenario and fold times. On the box's 14 November gates run at 57682257, before workers ran in parallel, preparing the template took 3.4s and all clones 16.9s together, against about five minutes of per-scenario database work before this change.

The lanes gate a change by the forge's `gates` flow, `.corpus/flows/gates.toml`, run at the branch's tip (`corpus flow run gates --at <commit>`): its ops are the org's check, `cella check org`, then `cella test`, and the site's check, `cella check site`, so the run logged over a commit is what a commit must pass and nothing else. Each op names what it reads (`reads` in `corpus.toml`): the site's check the site, the brand, the diagrams and what runs it (the CLI and the crate it builds on, the tools and their tests, the settings the text's guard reads, the flake, the manifests and the lockfiles), the org's check and tests everything but the site and the diagrams, whose manifests alone they read, as the feat check's edges and the install do. Corpus keeps an op's pass under the hash of what it read, and a later commit selecting the same files takes it (`kept`), so a change only in the site runs the site's check alone, in minutes, and takes the org's passes from the commit below it, and a change only in the org app takes the site's. Each runs in the devshell (`nix develop -c`), so a run needs nothing on the path but `nix`, in a lane's checkout or the detached one `--at` makes. The check first fetches the lockfile's packages (`pnpm fetch`) into the pnpm store of the filesystem the checkout is on, which `cella`'s offline install reads; `cella test` first starts the dev cluster on ports of the run's own (`CELLA_PGPORT`, `CELLA_ANALYTICS_PORT`), so runs at once never meet on one, and stops it after, pass or fail; its e2e scenarios run across workers at once, each on a database and a server port of its own, their number set by a worker's peak memory measured on the box, so two gates runs at once stay inside the builds slice's cap; an e2e scenario that starts an analytics shell of its own takes its port from `CELLA_ANALYTICS_PORT`, which the run sets a hundred higher for each worker after the first, plus an offset of its own, never a fixed one, so it too meets no other run's, nor another worker's. Measured on the box on 14 Nov 2026, under the other lanes' load, a load average of 11 to 18 on its eight cores: the e2e at one worker peaks at 1.75 GB of anonymous memory, the cluster's with it. With each scenario's browsers at once, three workers peak at 5.9 GB, for under a minute at the start, where the longest three, `a11y`, `editor` and `reads`, are dealt together, and stay under 4.5 GB after, so three, the default, hold about inside half the builds slice's `MemoryHigh` of 11G, and four would not; at three the 82 scenarios take 20 minutes, against 36 one after another, 28 of them the scenarios' own and 14 renewing, seeding and folding their databases, bounded by the longest, `a11y`, 9 minutes with its three browsers at once, against 12 alone and 18 under that load one after another. The e2e scenarios drive the browsers `BROWSERS` names, all three by default, on bacillus as on any host: the box's software GL driver, Mesa's EGL vendor under `/run/opengl-driver`, gives WebKit an EGL display, so a run there narrows no browser. Cella declares its flows rather than leaving corpus to infer them from `Cargo.toml` and `package.json`: the forge's `test` flow on a push runs the org's check, the whole suite and the site's check, and no flow runs a bare `cargo test`, `cargo fmt --check` or `npm test`, which gate nothing `cella` does not. A lane's gates run the e2e scenarios its change reaches: their `cella-test` op runs `cella test --since` the commit where the branch leaves main, so a change in one feat runs the scenarios reaching that feat, and one in a shared file runs them all ([tests](../../../_corpus/doc/architecture.md#tests)); its pass is kept under its own name, never taken for the whole suite's. The whole suite is the op `cella-test-all`, `cella test` with no `--since`, which the `merge` op needs in its place and the `test` flow on a push of main runs, so no version reaches main unjudged by every scenario, and a scenario selection missed is red on the train, never on main. Measured on the box on 15 Nov 2026, a change to one feat, `contact`, reaches 34 of the 86 scenarios: 19 import the shell's source, 7 cover all, and 8 reach `contact` or a graft joining it; its e2e takes 5.8 minutes on three workers, bounded by `a11y`, which covers all, at 5.8 minutes alone, against 12.4 minutes for all 86 at the commit below, and its whole `cella-test` 15.8 minutes, the unit suites before the e2e unchanged at about ten. The `merge` op, the box's integrator's pass (`corpus flow run merge`), needs the org's check, `cella-test-all` and the site's check, so a version the integrator merges has passed them composed with the versions ahead of it, and is judged by nothing else, drift among it. The `scale` flow, `.corpus/flows/scale.toml`, on a schedule of `every 24h`, runs `cella test scale --members 1000` over main's head on the box, the fold's scale tier at about a million entries; the tier's full size, about ten million entries and 44 GB, runs by hand, since it takes hours, and passed on the box on 14 Nov 2026 ([tests](../../../_corpus/doc/architecture.md#tests)).

The site, the brand and the diagrams are decoupled: `corpus.toml`'s `[review] decoupled` names `apps/site/**`, `packages/brand/**` and `packages/diagrams/**`, and the release reads it both ways: a change touching none of them lands on its green gates though main moved since only in those paths, and a change touching only them lands on its green gates though main moved since only outside them, so an org landing never sends a site change back to gate again, nor a site landing an org change. A change touching both rebases and gates again wherever main moved, as every change does where main moved in what it touches. The org app's styles import `@cella/brand`'s tokens and fonts, and the org's check runs the brand check, so a decoupled commit can still change what org renders or what a check reads: the `test` flow a push of main runs, the org's check, the whole suite and the site's check over main's head, is what catches one that breaks them.

## Tests

`tests/help.rs` walks the command tree and runs the built binary's `--help` for every command, checks clap's own consistency, that an unknown command exits 2, and that `key init` writes an owner-only 32-byte key and refuses to overwrite it. `src/test.rs` checks that a test file is placed by where it sits: a slice test in a feat's or graft's `_tests/`, an e2e scenario in an app root's `_e2e/`, and nothing elsewhere. `tests/fold.rs`, on the dev cluster, writes a scope's circles by signed writes as their handlers write them, a write rolled back among them, and folds its log: the copy verifies and matches it row for row, with a checkpoint every three entries; a fold stopped at a checkpoint and resumed there reaches the state a fold from the first entry does, and one resumed elsewhere, or after its state changed, is refused; an entry written before a fold's second version folds by the first and one after by the second, and a tree lacking the second refuses to fold past it; and a row the log does not carry fails the compare, which shows it on each side. `src/fold.rs` checks that the state hash reads the rows in their order and each table apart, and that a compare's merge names the rows only one side holds. `src/site.rs` checks the release against a checkout of its own and a directory standing in for the host: a release swaps the `current` link to main's head and keeps three builds; one whose served commit holds the same site, brand and diagrams builds and writes nothing, and a change to the brand releases; and a working tree that differs from its commit, by a tracked file or an untracked one, and a `HEAD` off `main` are refused before anything is built. `tests/seed_story.rs`, on the dev cluster, seeds a fresh database with Lanterne and one story at a time, and finds what each made and that its log verifies: governance's motions closed, and a second seed refused;
